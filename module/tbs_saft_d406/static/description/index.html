Romania SAF-T D406

Generates Romania's D406 SAF-T declaration straight from your Odoo accounting data — on Odoo Community, with no account_reports and no Enterprise subscription. Every generated file is checked against ANAF's official XSD, and the output is built to pass DUKIntegrator, the validator a real submission goes through. Free and LGPL-3.

What it does

Periodic declarations

Produces the periodic SAF-T declarations — L and T, plus their NL / NT non-resident variants — for any period you choose, from an export wizard.

Official ANAF nomenclatures

Six ANAF nomenclatures (4,182 rows) generated from ANAF's own published workbook — accounts, tax types, tax codes, invoice types, payment methods and units of measure — including the 21% / 11% VAT rates in force from 2025-08-01.

Chart mapping with override

Each account resolves to its ANAF statutory code automatically, following the resolution rules the official validator applies. Anything that cannot resolve is surfaced up front, and you can set a code by hand per account.

Romanian trial-balance semantics

Opening and closing balances follow Romanian practice: profit-and-loss accounts restart at the fiscal year, balance-sheet accounts carry forward. Accounts with no balance and no movement are left out instead of padding the file.

Validation before you submit

Every export is validated against the official ANAF XSD shipped with the module, with the offending element named when it fails. If you also run DUKIntegrator locally, the module hands the file to it as well.

Fails loudly, not silently

When a mandatory value is missing, the export stops and names the record and the element, instead of writing a file that comes back from ANAF as an unexplained rejection days later.

What it does not do yet

This module produces the periodic declarations only: L, T, NL and NT. Please read this before you buy into it as your complete SAF-T solution — it is deliberately narrower than the full D406 surface.

Declaration A (annual, fixed assets) and declaration C (on demand, stock) are not produced yet. They need fixed-asset and stock-valuation data that Odoo Community does not provide on its own. Rather than emit an incomplete file that ANAF would reject, the generator refuses those declaration types outright and tells you why.

Both are planned, and nothing in the module's architecture blocks them — but today, if you need A or C, this module does not cover you.

Where the schema and the validator disagree

ANAF's published XSD and ANAF's own DUKIntegrator validator contradict each other in four places. A file that satisfies the schema is rejected by the validator, and the validator is what decides whether your declaration is accepted. The module resolves each case in the validator's favour, then swaps the namespace in memory so it can still run the full schema check on every export — you get both.

External services

Nothing leaves your server

This module makes no outbound network calls. It reads your accounting data, builds the XML and validates it against the ANAF schema bundled inside the module — all locally. Your accounting data is never sent to TBS, to ANAF, or to any third party by this module. Filing the declaration stays a step you perform yourself.

DUKIntegrator is optional. If you install ANAF's own DUKIntegrator tool (a Java program ANAF distributes, not included here) on the same server, the module can additionally hand it the generated file for a full business-rule check. That runs as a local subprocess on your machine — still no network call, still nothing sent anywhere. Without it, you simply lose that extra check; the export itself works fine.

Frequently asked questions

Does this need Odoo Enterprise?

No. Odoo's own SAF-T support is built on the Enterprise account_reports General Ledger, which Community does not have. This module aggregates the ledger itself, in SQL, and depends only on account and l10n_ro. It installs and runs on Community, and works on Enterprise too.

Can I file the A (annual) or C (on-demand) declaration with it?

Not yet — see "What it does not do yet" above. Those need fixed-asset and stock data Community does not supply, and the generator refuses them explicitly rather than producing an incomplete file. Only L, T, NL and NT are produced today.

Is the generated file actually accepted?

Files generated from our test data validate against the official ANAF XSD and pass the real DUKIntegrator with zero errors. That said, your chart of accounts and your data are your own: run the export on your period, check the totals against your balance sheet with your accountant, and validate with DUKIntegrator before you file. We make no claim about a submission we have not seen.

Do I need DUKIntegrator for this to work?

No. The module generates and schema-validates on its own. DUKIntegrator is an optional extra check, run locally if you have it installed. ANAF distributes it; it is not bundled with this module.

Is any of my accounting data sent anywhere?

No. The module performs no outbound network calls at all. Everything — generation, schema validation and the optional DUKIntegrator run — happens on your own server.

What if an account will not map to an ANAF code?

You get told before the export, not after ANAF rejects it, and you set the code by hand on the account. This is worth knowing about: Odoo core itself creates two technical accounts with a 999 prefix (Cash Difference Gain and Loss) and ANAF has no 999 class, so nearly every Romanian Odoo database has at least those two to override.
